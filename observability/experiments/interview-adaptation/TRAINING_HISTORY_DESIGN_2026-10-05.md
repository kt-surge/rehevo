# 文字与语音训练任务回流：方案与自评审

## 需求与缺口

语音评估已保存 training_tasks_json，文字新会话仍只读取文字报告。两者字段相同，但下一场文字出题与 PREP 计划拿不到语音任务。完整 S4 需要这条已有功能的连接。

成功条件：只存在语音训练报告时，下一场相同岗位/简历的文字训练读取到任务，按原优先能力编排规则进入出题与计划；文字、语音结果按场次时间统一排序。通用模式仅读取没有简历关联的场次，不能混入其他简历。失败或尚未完成的语音评估不回流；坏 JSON 不阻断其他场次。

## 方案

在现有 InterviewPersistenceService.getRecentTrainingTasks 内统一读取：最多 10 个已评估文字会话、最多 10 个评估已完成的语音会话；按 Skill 与精确 resumeId（包括 null）限定。语音评估按会话 ID 批量读取，不逐场查询。两路按会话创建时间倒序，稳定并列顺序，解析并筛选有效 competency，最终仍最多 20 个任务。保留既有 TrainingTask DTO、出题输入和计划算法。

旧方法 A 保存实际源码；为同一失败回归只增加未使用的两个 repository 依赖及查询签名，不改变旧读取方法。B 使用这些依赖统一回流，不能把 A 写成 Git HEAD。

## 评审与验证

由执行 Agent 自评审：改动落在已有业务 Service 与 Repository，没有 LLM/外部 HTTP，不增加数据库事务；最多三个查询，避免循环调用数据库。不增加新评估模型、训练任务体系或复测类型。

先证明旧实现丢失语音任务的失败回归，再验证候选全量后端；H2 真实 JPA 校验 Skill、resumeId/null、评估状态、排序、坏 JSON 和两路合并。用实际 InterviewPlanService 验证任务能进入 requestedFocusCompetencies。这些不是实际模型语义质量或完整产品验收；之后仍须实际出题/评估/回放/文字复测。

保存 A/B、原始 XML/日志、输入、实际用量（本阶段模型调用 0）、失败与采用决定。不得修改已封存目录。正式浏览器语音采集仍受追问质量门约束，S0–S4 总范围保持不变。
