# 向量化任务版本隔离：下一项设计与自审

状态：本设计已实施并完成真实竞争对照及协议回归，见 [实现与结果](VECTOR_GENERATION_RESULTS_2026-10-01.md)。以下第 1 节保留实施前审计快照，第 2–5 节为当时方案与验收门。复核主体为当前 Agent 自审，不是独立评审。持久化投递恢复仍是下一阶段。

## 1. 当前可触发的入口与风险

真实入口为 `POST /api/knowledgebase/{id}/revectorize`。`KnowledgeBaseUploadService.revectorize` 在事务外下载并解析文件，随后把文档设为 PENDING，再发送只含 `kbId/content/retryCount` 的消息。初次上传也通过同一生产者入队。

消费者在开始时检查文档是否存在、是否 COMPLETED，然后单独写 PROCESSING，执行 Embedding、提升向量，再单独写 COMPLETED。`KnowledgeBaseVectorService` 的临时 `jobId` 只隔离每次执行的临时片段，没有在父文档中记录哪次请求当前有效。

已实现的短事务行锁可以把向量提升与父文档删除串行化；它只检查父文档存在。新一次重向量化开始后，旧请求的提升、COMPLETED/FAILED 写回以及重试消息仍没有版本限制。这是源码确认的可竞争窗口，尚未以真实并发实验复现，不写成已测故障或已解决问题。

## 2. 方案

| 部位 | 修改 | 必须满足的条件 |
| --- | --- | --- |
| 父文档 | 增加持久化 `vector_generation`，标识最近接受的请求 | 不能使用进程内变量或 Redis TTL 作为最终版本依据 |
| 开始请求 | 短事务设置新 generation 与 PENDING，返回 generation | 文件下载/解析在事务外；并发开始必须原子决定当前有效请求 |
| 消息 | 携带同一 generation；重试原样沿用 | 重试不得产生新版本，旧消息不得自动绑定当前版本 |
| PROCESSING/FAILED | 根据 `id + generation` 条件更新，返回实际影响行数 | 旧版本状态不得覆盖新请求；已删除文档直接丢弃 |
| 正式向量提升 | 在短事务锁定父文档后校验 generation；匹配才替换旧索引 | 不匹配时只清理本次临时 jobId，不能清理新请求的临时片段 |
| 完成状态 | 与向量提升放在同一事务，按 generation 写 COMPLETED/chunkCount | 防止向量已提交而旧完成写回越过新请求开始；外部 Embedding 仍在事务外 |
| 旧任务退出 | 明确返回 obsolete/deleted，模板记录 skipped 并 ACK | 不能误计为 SUCCESS，也不能重新创建旧版本重试 |

generation 是请求版本，jobId 是一次执行的临时向量批次，二者不能合并：同一请求因重试可有多次执行，但都受同一 generation 约束。

## 3. 迁移与兼容

先提供显式、可重复检查的数据库迁移文件与回滚说明，不依赖生产 `ddl-auto=update`。迁移兼容已有 COMPLETED 文档，原始索引不需重新 Embedding。

无 generation 的历史消息不能被悄悄认领为当前版本。具体迁移策略必须先检查现有队列与 PENDING/PROCESSING 文档：对未完成旧消息给出受控迁移/重新入队清单，确认旧消费者已停止后切换；未完成数据不能直接 ACK 丢弃。实验只处理本实验创建的文档与消息，不扩大到用户真实库。

新增版本隔离不能解决数据库提交后 XADD 前退出的投递缺口。这个窗口由后续 outbox/持久化任务恢复方案处理，不能借版本字段宣称已可靠投递。Redis MAXLEN 裁剪与多个工作进程并发回收也仍需单独故障实验。

## 4. 实验顺序与通过条件

1. 保存当前 A 组源码、数据库结构、有效配置与实验输入。用真实 PostgreSQL/JPA/Redis，加带屏障的确定性 VectorStore，复现旧任务在新请求之后提升或写回的窗口。先确认失败来自实际业务竞争。
2. 实现 generation 条件写入与原子提升/完成，再跑完全相同的场景；不改变 Embedding、切块与重试次数。
3. 至少覆盖：旧执行迟到提升、旧执行失败写回、新旧消息乱序、重复消息、重试版本不变、删除期间临时片段清理、完成后 ACK 前真实崩溃，以及迁移兼容路径。
4. 验证最新请求的正式向量内容/ID、generation、状态、chunkCount；验证旧任务的临时片段与 Pending 最终处理结果。不能只断言没有异常。
5. 故障与迁移门通过、默认后端 fresh run 通过、四篇公开资料原始索引指纹保持一致后，才保留生产改动并更新结果报告。

## 5. 自审结论

条件通过，可进入 A 组竞争复现。审查后补入了三个约束：完成状态必须与提升原子提交；旧消息不能推断当前版本；版本隔离不能替代持久化投递恢复。版本检查不能仅发生在开始时，否则 Embedding 期间的新请求仍会被旧结果覆盖。

短事务的行锁依据 PostgreSQL 的并发控制语义；事务之外发生的供应商调用不受这把锁保护。锁能实现的范围与必须实测的竞争结果应分开记录。[PostgreSQL 16 行锁说明](https://www.postgresql.org/docs/16/explicit-locking.html)
