# 持久化向量任务：接受、投递与正文恢复阶段结果

## 1. 结论与当前决定

**保留候选实现，默认开关继续关闭。** 同一修正后用例，在真实隔离 PostgreSQL/JPA/Redis/独立 JVM 上复现两个永久停留 PENDING 的场景；旧实现 2 项均失败，候选 2 项均通过，恢复原正文且各调用一次 Embedding 替身。

这一结果支持持久化正文、原子接受和投递恢复的正确性，不支持生产可靠性、恢复速度、模型调用恰好一次或 RAG 质量结论。恢复用例明确调用实际 `recoverOnce()`，没有运行实际定时扫描。执行租约、持久化业务重试预算和入队后状态写回前崩溃仍需验收，D1/D2 尚未全部退出。

本报告记录首批时点；随后另有 [真实入队后退出与实际调度补充结果](NOTIFICATION_CRASH_RESULTS_2026-10-02.md)。补充门不覆盖本批证据，最新接续以总目标第 10 节为准。

证据目录：[durable-delivery-20261002](runs/durable-delivery-20261002/)。258 个封存成果哈希、当前冻结源码及已读取敏感值检查均为 0 差异/命中；后端恢复 TOKEN800、健康 UP，原四份公开资料 24 块索引指纹保持 `76d903d460a4f34c5f3fedcc1e31b998cb999a6fb8d2ad6105760c1ed30b495b`。

## 2. 改动与用户价值

原链路在数据库接受请求与 Redis 入队之间存在进程退出窗口；Stream 正文被裁剪后，即便 PEL 还记得消息 ID，也无法靠该消息恢复原文。

候选将队列作为通知入口，增加数据库任务快照，保存请求版本、正文及 SHA-256、切块模式和 Token 上限。初次上传的文档与快照同事务接受；重新向量化接受新版本，同时使旧 ACTIVE 任务失效。Redis 调用在事务外，投递失败保留可恢复任务；短事务认领采用数据库时间、投递租约、fence 及 `SKIP LOCKED`。正式索引、文档 COMPLETED 和任务 COMPLETED 在同一事务提交。

目前扫描每次最多认领一项，投递失败固定等待 2 秒，正常重通知默认等待 30 秒，认领租约默认 10 秒。上述为配置值，**没有作为实测 SLA**。终态正文保留、批量吞吐与退避策略仍待实现；当前正文随父文档级联删除。

## 3. 对照实验与公平性

这份 HTTP 验收只证明默认关闭时的接线兼容，不证明持久化恢复已经正式启用。短合成样本不构成检索质量或延迟 A/B。

## 6. 评审与下一门

本次仍为执行 Agent 自审与原始证据核验，未宣称独立人工或其他 Agent 评审。候选开启条件尚未满足：

1. 真实 XADD 已成功但投递记录尚未写回时退出，验证重复通知的有界恢复。
2. 多工作进程执行认领、心跳、租约丢失与提交 fence；同版本重通知不能同时产生有效执行。
3. 业务尝试次数落库，通知重建或裁剪不能重置付费调用预算；失败与可恢复未完成状态分开。
4. 实际定时扫描及重启验收、配置/模型快照边界、终态保留和投递吞吐；不允许公共无正文 begin 绕过 durable 接受。
5. 对象存储失败补偿与删除故障另做实验。

下一阶段先完成第 1 项，再实现 D2 的执行权与重试预算。语音真实响应和 RAG 检索/生成效果仍是总目标的核心；本轮后端门不能代替这些效果验收。
