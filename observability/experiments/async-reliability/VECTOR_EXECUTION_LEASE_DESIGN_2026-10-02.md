## 1. 必须解决的实际缺口

设计前同版本通知在 `markProcessing` 后仍可进入 PROCESSING；本轮对照复现两名消费者同时调用 VectorStore，以及旧执行抢先提交。投递租约仅防止两个恢复扫描者同时发通知，不约束外部计算。候选实现增加有效执行权与提交围栏；不能据此推导供应商远端恰好一次。

每条新通知的 `retryCount` 可从 0 开始，恢复扫描重建通知后可能突破业务重试上限。必须将接受请求的执行尝试预算存入数据库，并保留原 generation。

## 2. 设计决定

| 对象 | 具体实现要求 |
| --- | --- |
| 固定任务快照 | 增加快照版本；正文、SHA、切块配置保持固定。Provider/model/dimensions 的快照能力先核对当前固定 VectorStore 注入链，不保存 API Key；不能静默恢复到另一模型 |
| 执行记录 | 在任务行增加 `execution_owner`、单调递增 `execution_fence`、`execution_lease_until`、`execution_attempts`、`last_execution_error`，与投递字段区分 |
| 认领 | 短事务按父文档→任务行固定顺序加锁，核对有效 generation/ACTIVE/预算及执行租约；每次获得执行权先增加持久化 attempts，返回不可变执行凭据 |
| 预算 | 默认初次加 3 次重试，共最多 4 次“获得执行权”。拒绝重复通知、投递失败不消耗执行预算；新通知不能重置次数。该预算不等于供应商实际 HTTP 次数，SDK/分块批次需另计 |
| 心跳 | 专用受 Spring 管理的有限调度器，复用明确配置的 TaskScheduler；数据库短事务续约，要求同 owner/fence、ACTIVE、当前租约尚未过期。不能让过期者自己重新续命 |
| 租约丢失 | 本地标记失权，停止后续分批计算并尽力取消本地工作；无法保证供应商远端取消。迟到返回只能清理本执行临时向量，不能提升或改父状态 |
| 提升完成 | 现有父文档锁内再锁任务；核对 generation+owner+fence+未过期租约，然后正式索引替换、文档 COMPLETED、任务 COMPLETED 一起提交。查询父状态或仅校验 generation 都不足 |
| 失败 | 失败回写同样校验执行凭据。尚有预算时清理本执行临时向量、释放租约并安排下一通知；耗尽才原子 FAILED。旧失败无法终止新执行 |
| 重复通知 | BUSY/过时/已完成的通知可 ACK，仅限数据库恢复依据仍有效；缺失快照或数据库失败保留 Pending。消费者模板要有明确结果，不能将“没获得执行权”计为正常成功 |
| 扫描恢复 | ACTIVE 且无有效执行租约、到达通知时间才重投递；有效执行者不反复收到通知。租约到期且预算耗尽时推进到清楚终态，不能永久 ACTIVE |
| 接受入口 | durable 开启时禁止无正文 `begin(kbId)`；保留旧模式兼容入口仅用于关闭模式。所有真实上传/重向量化走带快照接受 |

租约长度和心跳间隔按实际外部调用时间另做受控测量，先使用安全配置并校验心跳间隔显著小于租约；配置值不写成实际恢复 SLA。不要以长事务跨 Embedding 来避免竞争。

## 3. 数据库时间与锁等待自审

PostgreSQL 的 `CURRENT_TIMESTAMP` 固定于事务开始；`clock_timestamp()` 才反映调用时刻。若事务等待父锁之后仍按事务开始时间验租约，可能批准已经过期的工作。因此，D2 认领、续约和提交在获得相关锁后读取数据库当前时刻；租约校验使用该时刻，不能从调用者机器传入时间。这是对官方语义的工程推论，需要锁等待实验验证。[PostgreSQL 16 时间函数](https://www.postgresql.org/docs/16/functions-datetime.html)

投递扫描的 `SKIP LOCKED` 适合队列式领取，返回的是不完整并发视图，不可用于汇总全部任务状态或宣称公平调度；一次只领取一项的现有吞吐上限另作批量实验。[PostgreSQL 16 SELECT](https://www.postgresql.org/docs/16/sql-select.html)

心跳使用 Spring 提供的调度抽象及显式生命周期；全局定时器不能被长 Embedding 调用阻塞。调度成功不等于工作执行权有效，提交仍须数据库校验。[Spring 调度文档](https://docs.spring.io/spring-framework/reference/integration/scheduling.html)

## 4. 必须先复现，再修复的同用例对照

使用独立真实 PostgreSQL/JPA/Redis、两个实际消费者及确定性 VectorStore 栅栏。A 保存当前候选实际源码，B 只引入 D2；模型替身调用数和真正供应商请求数分别记录。新增目录不覆盖前阶段。

1. **同版本双通知竞争**：第一消费者停在外部计算，另一消费者读到第二通知；A 应复现重复计算，B 有效租约期间只有一次外部计算。
2. **过期旧成功**：第一执行停住，受控推进其租约过期，新执行完成；释放第一执行，正式向量 ID/内容和终态只能来自新 fence。
3. **过期旧失败**：新执行成功后旧执行抛错，旧失败不改变父状态/任务完成；原通知处理清楚。
4. **续约与失效**：真实续约阻止第二认领；停止心跳后可恢复。验证已过期者续约拒绝，并区分受控时钟推进与真实恢复耗时。
5. **通知不能重置预算**：反复失败加裁剪/重投递，最多 4 次执行认领；另验证进程在外部调用中退出仍已消耗一次预算，重启次数不回到 0。
6. **锁等待跨越租约**：实际数据库事务阻塞父锁，提交事务在等待期间过期；释放后必须拒绝提升，防止使用事务开始时间误判。
7. **原子提交失败**：任务完成写入实际触发器拒绝，正式索引与父状态回滚；失权清理只删除自己临时 job，不删除其他执行结果。
8. **故障兼容**：删除、重新向量化取代、入队前/后真实退出、裁剪、无版本旧消息、关闭开关、前向迁移/回滚，全量默认后端及实际 HTTP 入口。

## 5. 默认开启条件与明确限制

所有关键对照、回归与迁移门通过，实际定时扫描/重启推进有效；运行配置及恢复快照边界清楚，受控负载下没有吞吐或数据库连接池失控，再评审是否默认开启。私有正文不进入日志/公开证据；终态保留、批量扫描与退避需给出可配置策略。

即使 D2 通过，进程在供应商返回前退出仍存在结果未知，允许有预算的再次调用；不承诺外部计算恰好一次。租约隔离保证的是有效数据库提交权，供应商成本另以真实调用证据判断。
