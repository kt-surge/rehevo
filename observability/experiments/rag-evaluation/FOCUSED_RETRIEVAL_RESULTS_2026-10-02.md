# 扩大语料与有限分题召回：真实对照结果

## 1. 本轮决定

**不启用默认策略。** 有限分题召回在开发集补全两道比较题，但新来源、新主题 test 的必要证据覆盖没有提升，检索调用反而增加。候选仅保留为显式实验模式 `HYBRID_FOCUSED`，默认仍 HYBRID；下一轮转向正文定位与证据选择，不继续增加查询数。

本轮交付了新的实际语料、事实金标、来源/主题隔离的 test、可复跑的真实 API 对照及候选代码。尚未达到目标要求的有益 RAG 改进验收，不以开发分数代替泛化或回答质量。

A/B 共享实际应用、Embedding 模型、UUID、原始问题、关闭改写、RRF k=60 / 权重 3:1、融合候选最多 20、最终最多 8 块、6,000 估算文字 Token。超预算块跳过，继续尝试后续完整块。Java 计数器独立核验全部最终片段的估算和，不超过预算。预算一致不代表每题用量完全相等，也不包含 Prompt/来源标签或供应商计费用量。

## 3. 真正的结果与代价

“完整覆盖”要求最终上下文同时支持该题全部必要事实及条件；资料不足题保留在调用/失败分母中，不能算作检索拒答成功。此次所有 91 条采集完整，没有 API 失败或遗漏；没有调用回答、评审或 TTS 模型。

| 数据集与模式 | 候选完整覆盖 | 最终完整覆盖 | 必要条件覆盖 | 向量检索调用 | 片段文字 Token 中位数 |
| --- | --- | --- | --- | --- | --- |
| 开发 A：HYBRID + 同预算 | 52/53 | 48/53 | 85/90 | 65 | 5,797 |
| 开发 B：有限分题 + 同预算 | 53/53 | 50/53 | 87/90 | 105 | 5,838 |
| 新 test A | 22/22 | 21/22 | 36/37 | 26 | 5,581 |
| 新 test B | 22/22 | 21/22 | 36/37 | 46 | 5,584.5 |

开发中改善的两题为 `expanded-dev-cross-01`（anyOf 与 invokeAny）及 `expanded-dev-cross-02`（allOf 与 invokeAll）；没有新增整题退步。test 没有整题变化。调用数为实际 VectorStore 搜索调用，不是供应商 HTTP 尝试数；内部 HTTP 重试与费用未独立计量。

每种模式按顺序各扫描一次，时间只作诊断：开发 A/B 的 P50 为 238/297ms、P95 为 547/822ms；test 为 239/300ms、392/874ms。不是随机交错、多轮配对的性能实验，不能宣称因果延迟改善或稳定 P99。质量没有新 test 收益，已足以否决默认启用，不再追加无目的的性能扫描。

最初无预算的开发诊断为 47/53 最终完整覆盖；统一预算后的 A 为 48/53。这是预算选择的独立变化，不能算进分题召回的两题收益；尚未独立验收预算调整的生成效果。

## 4. 为什么仍然遗漏

辅助查询能找回材料，但“每条查询相关”不等于“最终上下文包含全部必要证据”。残留必要证据在各自辅助查询中的首次完整覆盖排名：

| 样本 | 辅助查询内完整证据排名 | 合并后缺口 |
| --- | --- | --- |
| 开发 Redis 恢复 + Spring 回滚 | Spring 条件第 5 | 合并第 12，最终未覆盖 |
| 开发取消比较 | CompletableFuture 条件第 5 | 合并第 9，最终未覆盖 |
| 开发事务代理 + async 执行器 | async 条件第 7 | 合并第 13，最终未覆盖 |
| test 文件流 + HTTP 异步 | Files.lines 条件第 7 | 合并第 13，最终未覆盖 |

这支持把下一轮问题放在**方法正文/目录摘要的区分、技术标识定位，以及同预算内必要证据选择**。不能靠再多发几条查询或加大 Token 掩盖排序。上述 test 诊断发生在结果之后，没有据此修改本轮策略。

新材料中取消语义保留了实现差别：通用 CompletableFuture 与默认 HttpClient 返回的可取消 Future 不能混为同一种中断保证。这些条件直接依赖各自[Java 21 API 原文](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.html)，不能靠相似方法名代替证据。

## 5. 验证与原始证据

- 最终候选全量后端 **310 项 fresh run，0 失败/错误/跳过**，含 7 项新增计划/范围/预算回归。首次三个失败来自新增测试装配未提供相似度，原日志与 XML 保留；修复装配后全量重新执行。
- 实际默认检索抽查 6 题：全部仍为一次向量检索、无辅助查询、无强制预算，片段集合 6/6 不变、顺序 5/6 一致。一个样本的两个片段发生排序对调；初次过强“全序不变”检查失败被保留，复用原观测记录差异，未重跑擦除。不能声称分数或全序完全一致。
- 实际接口拒绝 `contextTokenBudget=0`。默认配置不变，未改模型、切块方式、向量数据库或重排开关。
- Gold 标注曾遇到锚点歧义，发生在冻结及首次 test 检索之前；没有评分后改标。首次 Token 启动参数错误和 XML 长路径保存失败也保留为准备问题，不能当作有效试验。
- 两组实际 Provider/检索配置及执行源码逐项相同；test 前冻结源码到 test 后仍一致。dev 运行器后来只澄清一个报告句子，旧版本恢复成精确原执行 SHA 并单列，检索逻辑未变。

## 6. 接续计划与评审

评审结论：**开发诊断通过，新材料收益门未通过；不批准默认切换。** 保留显式实验模式和可复跑输入，后续候选不能默认开启。没有新的答案忠实度、RAGAS、用户起播速度或生产收益，不写入简历为稳定成绩。

1. 在开发残留切片先区分“正文未进候选”和“正文在候选但选择丢失”，检查目录/方法摘要的冗余。技术标识必须来自实际解析内容，不能按题号、Gold、文档 ID 硬选答案块。
2. 比较无需增加 Embedding 调用的正文定位/冗余去除与有界证据选择，维持相同块数和文字预算；保存必要证据改善、单主题退步与成本。
3. 冻结下一轮策略后，另备来源/主题隔离的新 test。当前 26 题后续只作已暴露回归，不能再次宣称同一轮新 test。
4. 检索真正通过收益门后，固定实际上下文单独验证生成忠实度、必要事实覆盖、引用和拒答，再验实际产品入口。语音真实同模型链路另行接续，整个持续目标保持 active。

拆分思路的一手依据为[微软检索阶段指南](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-information-retrieval)。本轮结果表明该方向仍须项目实际证据验收，官方做法本身不构成收益。
