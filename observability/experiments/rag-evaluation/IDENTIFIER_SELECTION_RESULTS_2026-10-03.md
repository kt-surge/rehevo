# 技术标识正文选择：质量收益与耗时门复测

## 1. 本轮决定

**有受控必要证据收益，成本门未通过，继续优化；不默认开启。** 新策略不再增加查询数，通过当前候选的技术标识与正文线索选择完整块。扩大开发集和新来源/主题测试都补回了必要证据，没有新增整题退步；随机交替的真实接口复测中，P95 增幅约 18.6%，超过预设 10% 门槛。保留显式实验模式 `HYBRID_IDENTIFIER`，默认仍 HYBRID，下一轮先降低正文识别扫描开销并复验成本。

这不是已经完成的 RAG 整体优化成果：生成忠实度、完整性、引用、拒答、SSE 和实际产品入口仍待验收；真实语音性能与完整 S0–S4 目标继续推进。

## 2. 实现与冻结顺序

- 原始问题只执行一次向量搜索和一次现有词法搜索；原 RRF 的 20 个候选保留。标识与正文选择只影响最多 8 个最终完整块，不改原文、不补发 Embedding、不使用金标/题号/文档 ID 选答案。
- 最长 512 字问题、最多 8 个标识，最多预留半数位置且不超过 4 块；正文线索为独立名称行及随后同名签名。这个启发式不能保证所属类、完整正文或语义正确。其余位置按原排名填充，跳过超预算整块。
- A/B 同实际应用、模型与公开资料 UUID，关闭改写/重排，RRF k=60、权重3:1、候选20、块数8、6,000估算文字Token。独立 Java 计数结果核验全部实际最终上下文；不包含 Prompt/来源标签，不当供应商账单。
- 源码通过 316 项 full fresh run 后冻结，随后才打开新测试来源；事实和题目在首次 test 检索前冻结。测试后没有修改候选、金标、删题或按结果调规则。
- 新材料是 Java 21 Matcher、Python 3.13 heapq/bisect 的官方原文；URL、主题组、完整原文指纹与开发集和已暴露的上一轮 test 不重叠。**同一执行 Agent 知道策略并编写、原文自审金标；不是独立执行者盲测、人工评审或随机用户抽样。**

冻结与时间顺序证据见 [序列记录](runs/identifier-selection-test-20261002-r1/sequence-evidence.json)。候选指纹在采集、配对复测和最终核验期间保持一致。原始 UTC 时间保留，不重写跨日记录。

## 4. 耗时门：没有通过

最初顺序各扫描一次，只作诊断：开发A/B P50约249/276ms、P95约525/427ms；test约205/237ms、441/559ms。方向随输入变化，不能选开发的较低P95宣称更快。

为检查这一具体风险，固定相同策略与27个test问题，预先生成种子61002的随机题序、同题A/B随机先后，执行4轮，每组108请求。全部216请求完成、缺失0，实际模型、源码和参数未变；独立核对原始响应、调用数与预算。**重复题是性能观测，质量样本数仍为23道可回答题。**

| 本会话随机配对复测 | A | B |
| --- | --- | --- |
| 实际请求 | 108 | 108 |
| P50 | 206.89ms | 222.42ms |
| P95 | 388.75ms | 460.94ms |

P50增幅7.5%，P95增幅18.6%，未通过当前10%成本门。按题整体保留两组及重复次数做聚类重采样，P95增幅95%区间约[-6.1%,60.5%]，不确定性较大；这是同会话的初步成本证据，不能称为跨三个独立时间窗、生产分位数或确定的因果慢18.6%。当前也没有足够证据批准默认启用。

首轮未节流，第三个请求触发真实接口每秒两次的限流（code8001），当即停止，保留2个成功/214个未完成分母。第二轮独立计划保持原随机顺序及策略，将请求开始间隔设为0.65秒；没有关闭限流或自动重试失败请求。两轮原始记录都保留，不能把第一轮当已完成性能试验。

复测证据：[完整采样结果](runs/identifier-selection-test-20261002-r1/paired-latency-r2/summary.json)、[原始响应核验](runs/identifier-selection-test-20261002-r1/paired-latency-r2/independent-raw-verification.json)、[首轮限流失败](runs/identifier-selection-test-20261002-r1/paired-latency-r1/summary.json)。

## 5. 正文选择本身的CPU诊断

固定92条真实B候选输入，在同一Java进程进行3轮热身、8轮随机配对，两组各736次选择，调用实际生产选择类与同一Token计数器；没有Embedding、数据库或API调用。原HYBRID的预算选择与随后追踪计数都纳入A；B使用实际正文选择。数据装配和最终元数据复制未纳入计时。

| 本地选择CPU | A | B |
| --- | --- | --- |
| P50 | 1.05ms | 4.62ms |
| P95 | 1.95ms | 7.97ms |

正文选择确有额外CPU开销，P95差约6ms。这能指向扫描优化，但**不能解释全部接口分位数差，也不能用组件结果覆盖未通过的端到端门**。后续优先减少有界正文模式的重复扫描和回溯，保持完全相同的选择语义；先证明等价，再复验实际接口。

CPU证据：[真实输入的组件结果](runs/identifier-selection-actual-dev-20261002-r1/component-cost-r1/summary.json)。这不是736道新题，也不是实时语音性能。

## 7. 接续评审

**质量样本门通过，当前成本门未通过；不批准默认切换。** 不使用“少一次Embedding”包装：两组始终都是一次，只是避免上一轮分题方案的额外调用。当前20/23也不能改写为回答准确率或RAGAS。

1. 优化正文线索识别实现，不改选择规则；用独立语义等价回归和全部冻结实际输入核对，再测组件与真实接口成本。若规则发生变化，当前test已经暴露，最终质量验收要另备新材料。
2. 保留全部三个新test漏证据样本与候选缺失开发样本，区分正文跨块、条件不在所选块及候选缺失，不能靠更多查询/Token掩盖。
3. 通过成本门后冻结实际上下文，分别评估生成忠实度、必要事实、引用支持和拒答，再验产品入口与SSE。供应商可用性需当轮实测，不能把旧额度失败当当前事实。
4. 真实同模型TTS帧流/连续播放/取消及剩余异步故障继续接续；全目标仍active。
