# 语音帧输出设计与自审

## 已确认的机会

当前句级路径等待 `synthesize` 返回完整 PCM 才发 WAV。SDK 的帧回调已经有可用首帧。
同模型、音色、语速和文本的 10 对真实诊断全部成功，10 对完整 PCM 哈希一致；中位首有效 PCM 从 916.51ms 到 429.90ms。
这是组件诊断，不是浏览器性能门，也不据此默认开启新协议。

## 接入方案

1. 新协议 `audio_frame` 明确携带句序、帧序、句末标记与 PCM s16le/24000/mono/16bit。句末独立空事件不计首音频。
2. SDK 回调只入队，独立消费者按句序和同句帧序写 WebSocket。后句提前完成不能插播；前句失败明确终止整轮。
3. 待处理句数与 PCM 总字节都有上限。满载立即报错，不能阻塞 SDK 回调或静默删音频。
4. 并发许可在工作线程中进行可中断、带绝对截止时间的等待，避免把无界等待放进 LLM 回调。
5. 每句 prepare 后先注册可关闭句柄，再 start。轮次持有管线，取消、断连及终态都会释放任务并中断等待线程。
6. 部分音频发送后禁止整句重播。新帧路径先使用明确失败语义，暂不自动调用不受该管线截止时间控制的旧整段降级。
7. `frame-tts.enabled` 默认 false。浏览器排程与真实 A/B 未验收前只在隔离实验开启。

## 自审与修订

| 风险 | 约束与验收 |
| --- | --- |
| SDK 回调相互关闭任务导致锁循环 | 回调只记录失败并唤醒消费者；任务关闭由消费者或轮次拥有者执行 |
| 帧被取走但 WebSocket 正在阻塞，总字节少算 | 写出返回后再释放该帧字节预算 |
| 注册句柄与取消竞态 | 关闭后的资源容器拒绝并立即关闭新句柄；任务 start 自身再次检查取消 |
| 取消发生在序列分配与实际写出之间 | 帧在实际出站锁内再次检查活动轮次 |
| 空句末事件被当作首音频 | 首音频仅记录非空有效 PCM，句末事件独立处理 |
| 小样本和无 usage 被写成漂亮指标 | 诊断单独报告；取消调用缺失 usage 标未知；正式组件与浏览器门继续保留 |

评审结论：可实施，须先通过乱序、缓冲溢出、部分失败、截止时间、许可等待取消与迟到回调回归。此为同 Agent 自审，非独立或人工评审。

## 真实预检后的修订

首轮真实单许可预检暴露“公平信号量不保证提交句序”：后句工作线程可能先建连，首句需要等待其完整合成。
已增加按提交序号进入许可等待的约束。第二轮真实取消/溢出均从首句启动，待排后句不调用SDK；正常两句音频/顺序保持一致。
最终完整回归72套件345测试通过。仍须浏览器及正式性能门，默认关闭决定不变。
