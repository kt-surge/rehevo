# 同句 TTS 帧流、取消与有序输出：实施和诊断结果

状态：保留候选实现，继续浏览器与正式 A/B。`frame-tts.enabled` 默认 false；整体 S0–S4 目标仍 active。

## 1. 实际做了什么

- 保留整句 `synthesize` 作为 A；新增 prepare → 注册可关闭任务 → start 的帧客户端。
- 每句有绝对截止时间、独立订阅与 SDK 连接；空音频、字节不对齐和部分失败都明确失败。连接关闭不再遗漏。
- 新增有序 PCM 管线：同句边接收边输出，后句提前音频进入有界队列。句数和 PCM 字节都有上限，正在写出的帧仍占字节预算。
- 并发许可按提交句序分配，等待可中断并使用提交时的绝对截止时间。SDK 回调只入队，避免在回调中同步关闭其他任务造成锁循环。
- handler 新增 `audio_frame`，包含句序、帧序、句末、PCM s16le/24000/mono/16bit 与既有 Turn sequence。实际写出锁内再次检查活动轮次。
- 取消、断连、暂停清理与终态都会释放轮次持有的帧管线。配置重载成不兼容采样率时在发帧前拒绝，避免协议误标。
- 新帧路径不跳过失败句、不对已发音频重播整段；失败进入明确终态。旧模式维持原行为用于对照。

设计及自审见 [设计与评审](DESIGN_AND_REVIEW_2026-10-04.md)。这些是源码实施与受控验收，尚未在真实产品 WebSocket/浏览器开启新协议。

## 3. 真实取消诊断

四场景：start前、建连期间、首帧后取消，以及100ms绝对截止时间。
本地关闭分别0.744/0.2901/0.1621/0.0038ms；每场景观察关闭后1000ms，产品回调迟到帧均0，启动工作线程均结束。
start前 SDK 调用0；其他场景的 SDK duplex 方法调用不必然等于服务端任务已启动。

SDK `close` 返回只表示本地接受关闭请求。没有观察到供应商远端取消确认；缺失终态 usage 记未知，不能当成0消耗。
这四次也不构成取消 P95 或浏览器实际停播指标。没有证据要求升级 SDK 或新增硬取消调用，暂保留已实测的 dispose + close。

原始记录：`runs/20261004-r2/cancellation-diagnostic-r1`。

## 4. 真实管线发现问题并修复

首轮真实管线预检 `ordered-provider-preflight-r1`：正常两句完整PCM与已冻结整句参考一致，顺序/句末正确；取消后没有新增输出，溢出明确失败。
但并发上限1的取消与溢出场景中，第二句先取得许可。这是因为公平信号量保证线程等待顺序，并不保证提交句序。
取消场景先完整合成第二句再等第一句首帧，拖慢首音，还启动了不必要的后句任务。此负结果保留，未删除或改写。

修复：按提交序号允许任务进入许可等待。新增回归故意延后第一句工作线程，先运行第二句工作线程；第二句必须等待第一句占用许可。

相同真实预检 `ordered-provider-preflight-r2`：

- 正常两句成功，17个音频/句末事件均按序，完整PCM仍与整句参考一致。
- 单许可取消场景先启动第一句，第一帧后本地关闭0.2933ms；仅启动第一句，关闭后1000ms未新增输出。
- 单许可溢出场景先启动第一句，明确失败且输出0；等待的第二句未调用SDK。
- 管线/音频/源码审计0错误；首句优先问题0。仍为受控诊断，不据此写稳定延迟收益或费用节省。

## 6. 保留决定与下一步

保留流任务、连接释放、有界按序管线、提交序许可和轮次资源清理。新帧模式继续默认关闭。
浏览器目前仍使用 `onended` 再启下一段的旧队列，尚未支持新 `audio_frame`。隔离应用18080仍是此前启动版本，不能把源码测试当作产品部署。

下一步按原目标推进：

1. 提取连续音频排程器，以 AudioContext 时间线预排下一片段，保留所有Source的轮次归属与取消能力；增加PCM格式/句帧序检查。
2. 接入实际排程起点计时，记录片段间隙、缓冲欠载、暂停/恢复、后台标签页、断连与取消；新协议只在隔离实验开启。
3. 正式组件和完整浏览器A/B分别冻结源码/配置/输入；每组至少100次、至少3时间窗，按文本分层，使用预先生成的随机配对顺序。10对诊断不替代正式门。
4. 保留原门：组件首有效PCM P95改善≥20%；浏览器提交→有效起播P95改善≥20%，P50不劣化>5%，间隙减少且无新增取消后播放/乱序/错误。
5. 接续RAG生成和业务完整流程，检索/生成质量继续分别评估，不用组件数字替代三条简历成果。
