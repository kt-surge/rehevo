# 完整追问与排队取消方案

## 已观察到的失败

r5 真实第二轮 120 字符回复停在“最终…”，主要问题没有问完。旧实现按字符硬切并提前取消上游，最终 usage 未到；当前 Handler 在执行器开始运行后才创建轮次，排队时取消仍可能启动模型。旧证据封存不改。

## 候选与评审

1. 提示词明确只问一个聚焦、完整、以问号结束的问题，120 字符包含技术条件，避免重述和评价。提示词移至 `.st`。不把“请继续”当有效面试问题。
2. 首个完整问题确认且符合字符预算后才提交句级 TTS；句号前的铺垫在确认前暂存。问完后的额外问题不播。超长或未闭合的问题不硬切，不发不完整 TTS；最多一次无工具流式压缩，保留原技术对象和条件。修复仍不合格则本轮失败，不虚构成绩。
3. 原生成和一次压缩共享绝对截止时间，单次请求有生成 Token 上限。有效问题得到后继续消费到流终态，使 usage 可观测；有界缓冲，异常和超时仍失败。取消通过处理线程中断解除阻塞。
4. 提交文本时就创建并推送轮次；执行器开始后先检查轮次是否仍活跃。已取消的排队任务不调用模型/TTS，也不复活轮次。拒绝提交时关闭资源并失败、释放 processing 状态。

评审取舍：确认问题后才播放铺垫，可能增加无用铺垫的首声等待，但首个有意义问题更可靠；压缩会增加耗时及成本，必须单列发生率。不能靠静音/占位句降低指标。先不更改帧流/连续播放默认开关。完整性修复在正式语音 A/B 两组中共用，避免把问题长度变化算成帧流收益。

## 预先冻结的验收

- 先跑旧实现失败复现，保存源码、失败 XML 与输出。新实现验证实际失败文本、任意 Token 切分、标识/版本、恰好预算、空/超长/未闭合输出、压缩失败、usage 终态消费、超时取消。
- 可控真实执行器排队：停止确认及时到达；释放队列后 LLM/TTS 调用数为零，无 turn_started 复活/COMPLETED；可继续下一轮。执行器拒绝不会永久占用 processing。
- fresh 全量后端回归；前端未改则不重复无关构建。
- 冻结候选与受控输入，再小批真实模型质量检验：完整聚焦问题、条件保留、无省略号/占位成功、用量终态、压缩发生率及逐次耗时。失败全部报告，不把该批当正式 P95。
- 只有质量与取消门通过才开始正式实际浏览器 ≥100/组、≥3 窗 A/B。真人听感/麦克风与 S2–S4 仍各自验收。
